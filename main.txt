==================================================
OFFICIAL ARCHITECTURE
==================================================

Request
→ API/schema validation
→ LLM interpreter
→ deterministic LLM-output guardrails
→ directive application
→ mathematical optimizer
→ independent plan validator
→ totals
→ API response

The LLM interprets language.

The optimizer performs mathematical scheduling.

The guardrails and schedule validator are deterministic.

==================================================
SUPPORTED DIRECTIVES
==================================================

The ONLY directive types are:

solar_reduction
minimum_battery_reserve
no_charge_window
no_discharge_window
max_grid_window
no_op

Do not add another directive type.

==================================================
CANONICAL INTERPRETATION FORMAT
==================================================

Each operator note produces exactly one object:

{
    "note_index": int,
    "applies": bool,
    "directive_type": str,
    "structured_adjustment": object | null,
    "explanation": str
}

Entries must remain in note_index order.

no_op:

{
    "note_index": ...,
    "applies": false,
    "directive_type": "no_op",
    "structured_adjustment": null,
    "explanation": "..."
}

Every real directive:

applies = true.

==================================================
TIME RULE
==================================================

All hour arrays:

- unique
- sorted
- integers
- values 0 through 23

Time windows are:

START INCLUSIVE
END EXCLUSIVE

Examples:

1 PM to 3 PM → [13, 14]
2 AM to 5 AM → [2, 3, 4]
6 PM to 9 PM → [18, 19, 20]
noon to 2 PM → [12, 13]
midnight to 3 AM → [0, 1, 2]

==================================================
SOLAR REDUCTION RULE
==================================================

factor means fraction REMAINING.

"solar falls to 20%"
→ factor = 0.20

"80% reduction"
→ factor = 0.20

"reduced by 25%"
→ factor = 0.75

"reduced to 25%"
→ factor = 0.25
